# LOGISTRIA — Build Brief

Autonomous multi-agent layer that sits on top of an existing ERP/SCM (no migration, no replacement).
Reference demo (2 agents, 3 hardcoded scenarios) is in /legacy_demo. Reuse its ideas, not its structure.
Do NOT copy the hardcoded API key found in legacy_demo/logistria_demo.py.

## 1. Flow (deterministic LangGraph state machine)

Admin clicks "Start Production" (product, quantity, due date, urgency)
1. InventoryAgent: read BOM -> check raw material stock via ERP adapter.
   - All available -> reserve materials -> ManufacturingStep.
   - Shortfall -> SupplierRankingAgent for each missing material.
2. SupplierRankingAgent: score suppliers (section 3) -> top pick + confidence.
3. ProcurementAgent: confidence >= 0.80 AND order value <= AUTO_LIMIT -> auto place PO via adapter.
   Otherwise -> status `pending_human_review`, graph pauses (LangGraph interrupt) until admin approves/rejects/overrides supplier in the UI, then resumes.
   Also review if: single-supplier dependency, price anomaly > 25% vs history, or any data missing.
4. ManufacturingStep: simulated production run with progress events (ERP adapter updates work order).
5. LogisticsAgent: after manufacturing, optimize delivery route (OR-Tools VRP, OSRM distances or haversine fallback); output ordered stops, ETA, distance, cost.
6. MonitorAgent (central): subscribes to ALL bus events; detects stalls, low confidence streaks, late deliveries, stock-outs, rate-limit failures; raises alerts and can pause/resume runs.

## 2. Message bus + War Room

- In-process async event bus, persisted to DB table `events`:
  {id, run_id, ts, sender, receiver, type, payload_json, human_text, severity}
- type: info | request | response | decision | alert | escalation | human_action
- Every event gets `human_text`: a plain-English sentence generated by the Narrator (LLM, cheap model) from payload; fallback = template string. Narrate asynchronously so it never blocks the pipeline.
- Stream to UI via WebSocket /ws/events (and REST GET /api/events?run_id=).
- War Room page: left = live conversation feed (agent avatars, sender -> receiver, human_text, expandable raw payload, severity colors); center = pipeline status graph for the active run; right = approval queue (approve / reject / change supplier) + alerts; bottom = chat box.
- Admin actions (approve, reject, override, chat command) are also events, so the feed is a full audit log.

## 3. Supplier ranking (computed in code)

Inputs per supplier: unit_price, lead_time_days, moq, on_time_rate, defect_rate, past_orders (n).
- Normalize price and lead time to 0..1 (lower = better) across the candidate set.
- Reliability with Bayesian shrinkage: rate_hat = (n*observed + K*prior)/(n+K); K=5, prior = portfolio average (default 0.85 on-time, 0.04 defect). New suppliers (n=0) get the prior.
- Weights depend on demand: urgency high -> lead_time 0.35, on_time 0.25, price 0.20, quality 0.15, moq_fit 0.05. Normal -> price 0.30, lead 0.20, on_time 0.25, quality 0.20, moq_fit 0.05. Configurable in settings.
- Cold start: add exploration bonus c*sqrt(ln(N_total+1)/(n+1)), c=0.10, capped at 0.12, so new suppliers get a fair trial but cannot win on bonus alone. Record `cold_start=true` on the result.
- Hard filters: moq > needed qty*3 or lead time beyond due date -> excluded with reason.
- Confidence (0..1) = 0.5*margin + 0.3*data_sufficiency + 0.2*constraint_fit
  margin = clamp((score1-score2)/0.15, 0, 1); data_sufficiency = n_top/(n_top+5); constraint_fit = 1 if no soft violations else 0.5.
- Output: ranked list with per-factor breakdown, top pick, confidence, cold_start flag. Then the LLM writes the explanation from these numbers only.
- After a PO is received/rejected/late, update supplier history (feedback loop).

## 4. Chatbot / demand-spike commands

- Chat box in War Room talks to an OrchestratorChat agent with tools: get_inventory, get_run_status, forecast_demand, simulate_spike(product, pct, days), start_production, list_pending_reviews, explain_decision(event_id).
- Example: "Demand for Product X will jump 40% next month" -> forecast_demand (statsmodels/Prophet or simple exponential smoothing on order history), compute material needs, show shortfall, propose a production plan, and ask admin to confirm before starting runs.
- Chat never executes money-moving actions without an explicit confirm button.

## 5. ERP/SCM adapter layer

Abstract `ERPAdapter` interface: get_bom, get_stock, reserve_stock, list_suppliers, get_supplier_history, create_purchase_order, update_work_order, record_receipt.
Implementations: (a) `MockAdapter` (SQLite seed data, default), (b) `ERPNextAdapter` (REST, API key/secret in .env), (c) `GenericRESTAdapter` driven by a YAML field-mapping file for other systems. Agents only call the interface.

## 6. LLM layer (LiteLLM, provider-agnostic)

- Default provider is Groq (already proven to work in legacy_demo). Config in .env: LLM_PROVIDER, PRIMARY_MODEL=groq/openai/gpt-oss-120b, NARRATOR_MODEL (a smaller, cheaper Groq model from the account's model list), FALLBACK_MODEL (optional, any other provider e.g. gemini/... or openrouter/...). Switching provider must need only .env changes.
- Free-tier budget is tight (about 30 requests/min, 8K tokens/min and 200K tokens/day on gpt-oss-120b). So: keep prompts short, send only the numbers an agent needs, use a global token-bucket limiter below those limits, and cache identical calls.
- Narration is TEMPLATE-FIRST: every event type has a plain-English template filled from the payload. Use the LLM only for escalations, alerts and supplier-ranking explanations (and chat). Never call the LLM once per low-severity event.
- Central wrapper: timeout 30s, 1 retry, fall to FALLBACK_MODEL on 429/5xx, then to the template text. The pipeline must still finish with no LLM at all.

## 7. Data model (SQLAlchemy)

products, bom_items, materials, inventory, suppliers, supplier_materials (price, lead, moq), supplier_history, production_runs, purchase_orders, deliveries, events, approvals, settings.
Seed script: 3 products, 8 materials, 8 suppliers (mix of established + new) so every path (enough stock / auto-order / human review / cold-start win) can be demonstrated.

## 9. Phases (do ONE at a time; stop after acceptance passes)

Phase 1 — Core backend: models, seed, MockAdapter, event bus, LLM wrapper with fallback, InventoryAgent, SupplierRankingAgent (scoring + confidence + cold start), ProcurementAgent with threshold + pause/resume.
  Accept: pytest passes; POST /api/runs with enough stock -> goes straight to manufacturing; with shortage -> ranking -> either auto PO (conf >= 0.8) or pending review; approving resumes. Cold-start supplier can win when established ones are poor.

Phase 2 — Manufacturing + Logistics + Monitor: manufacturing simulation, OR-Tools routing, MonitorAgent alerts, supplier history feedback.
  Accept: a full run finishes end to end; route output has ordered stops, distance, ETA; monitor raises an alert when a run stalls or a PO is late.

Phase 3 — War Room frontend: WebSocket feed, human_text narration, pipeline graph, approval queue, route map, start-production form, event audit view.
  Accept: starting a run shows agents talking live; escalation appears in queue; approve/reject works and appears in the feed.

Phase 4 — Chatbot + forecasting: chat agent with tools, demand-spike scenario, confirm-before-act.
  Accept: "demand for Product X up 40% next month" returns a shortfall and a plan; confirming starts runs.

Phase 5 — ERPNext adapter + hardening: ERPNextAdapter against a local ERPNext (docker), GenericRESTAdapter, auth for admin, Dockerfile/compose, README with demo script for 3 scenarios, error/rate-limit handling check.
  Accept: switching ADAPTER=erpnext in .env runs the same flow; demo script reproduces all paths.
